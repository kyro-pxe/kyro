# Plan and results for v0.2.0

What v0.2.0 adds to [v0.1.0-alpha](ALPHA.md), how each part was tested,
and what was not. What works, item by item, is in [ROADMAP.md](ROADMAP.md);
if this file and the roadmap disagree, the roadmap is right.

## In scope

| No. | Feature | Decided in |
| --- | ------- | ---------- |
| 1 | **Armings run out.** Every arming has an end, 24 hours by default (`arm_timeout`, `kyro arm --expires`, 1 minute to 30 days, no "never"). A client that boots later goes to its disk and is shown as `expired`. | [ADR 0006](adr/0006-arming-expires.md) |
| 2 | **Driver packs.** `kyro driver add`, `list`, `remove`; Windows PE loads the packs, and Windows Setup carries them into the installed system. `kyro driver fetch` downloads `intel-rst`, `intel-rst-11` and `virtio` from their makers with pinned checksums. `install.sh` offers Intel's driver and asks for its license. | [ADR 0007](adr/0007-drivers.md) |
| 3 | **Progress and failure reasons.** Windows PE reports over the install share that it connected the share, started Setup and, if so, that Setup failed. Setup's restarts are counted. A timeout says where the installation stopped. | [ADR 0008](adr/0008-progress.md) |
| 4 | **Values per client.** `{{var:NAME}}` in an answer file, `kyro arm --set NAME=VALUE`; arming without a needed value is refused, and values are deleted when the installation ends. | [ADR 0002](adr/0002-profiles.md) |
| 5 | **A built-in profile that installs nothing by itself** (`kyro profile import --example-interactive`), for looking at a machine and its drivers before installing it. | [README](../README.md#trying-drivers-without-installing) |

Fixes on the way: reports from Windows PE printed "The system cannot find
the file specified." on the screen; a Setup that a person closed was called
an error; a drivers directory made by the CLI on a server set up by the
alpha's installer was unreadable for the service.

## Out of scope

Unchanged from the alpha unless listed above. In particular: choosing
driver packs per client or per image, signatures for the release files, a
web interface that changes anything, BIOS clients, full DHCP, an external
SMB server, ARM.

## Acceptance tests

| No. | Test | How |
| --- | ---- | --- |
| B1 | A client armed with a short lifetime that boots after it is sent to its disk, shown as `expired`, and its disk stays empty | `make e2e` (step 5), unit and fuzz tests |
| B2 | On hardware that Windows has no driver for, the driver packs let Windows PE reach the share and Setup find the disk, and the drivers are in the installed system | `make e2e` with `KYRO_E2E_VIRTIO=1` and the packs `virtio` and `intel-rst`, and the same machine without packs as a check |
| B3 | While a client installs, its stage is shown; a Setup that ends with an error in Windows PE fails the client at once | `make e2e`, unit tests, a test with an SMB client |
| B4 | A value given when arming arrives in the installed Windows and is gone from the record afterwards; arming without it is refused | `make e2e` with `KYRO_E2E_VALUES=1`, unit and fuzz tests |
| B5 | With the interactive profile, Setup waits for a person, the disk is not partitioned or formatted, and closing Setup ends the installation | By hand in a virtual machine |
| B6 | A server installed with v0.1.0-alpha's published `install.sh` is upgraded by the new one and keeps its images, profiles, configuration and armed clients | Container |
| B7 | The acceptance tests A1 to A7 of the alpha still pass | As in [ALPHA.md](ALPHA.md) |

## Results

Nothing here is estimated.

| No. | Result |
| --- | ------ |
| B1 | Passed on 2026-11-16 (`make e2e`, 33 minutes): the second machine was armed with `--expires 2m`, booted half an hour later, was sent to its disk and shown as `expired`; its disk stayed empty. |
| B2 | Passed on 2026-11-16 (27 minutes): Windows PE loaded `netkvm.inf`, `vioscsi.inf` and `iaStorVD.inf`, the installation ran to the end, and all three drivers were in the driver store of the installed Windows. Without packs the same machine stopped in Windows PE: "The network location cannot be reached". |
| B3 | Passed on 2026-11-16 (29 minutes): `share-connected` and `setup-started` arrived 30 seconds after the installer was handed out, and Setup's restarts were counted. A real `setup-failed` was seen on 2026-11-17, three times, each time by closing Setup (exit code 1223). A Setup that fails by itself, and the reasons after a timeout, are covered by unit tests only. |
| B4 | Passed on 2026-11-16 (33 minutes): arming without the value was refused; the installed Windows asked for its address as `KYRO-E2E-VAR`; the value was gone from the record afterwards. Values that need escaping in XML were tried in unit tests only. |
| B5 | Passed on 2026-11-17, three starts by hand with virtio hardware and the packs `virtio` and `intel-rst`. Setup's disk page listed the disk. A prepared disk (GPT, FAT32, NTFS with files) was compared before and after two starts: partition table, FAT32 partition, unpartitioned space and all files identical; 337 sectors inside the NTFS partition changed, which is taken to be what Windows writes when it opens an NTFS volume. |
| B6 | Passed on 2026-11-27 in a Debian 13 container. The published `install.sh` of v0.1.0-alpha matched the published `SHA256SUMS`, downloaded its tarball from the release page and installed it; after the upgrade the image, the profile, the configuration and the armed client were still there, `drivers/` was created as `root:kyro` 0750, and a pack added afterwards was readable by the user `kyro`. Writing this test found the defect with the drivers directory; it was fixed first. |
| B7 | A1 to A4: passed in each of the four e2e runs of 2026-11-16, see below for what changed since. A5 and A6: `make test-installer` passed on 2026-11-27 on Debian 13, Ubuntu 24.04, Fedora 43 and under systemd; `shellcheck` runs in CI. A7: `make release VERSION=v0.2.0` passed on 2026-11-27; whether the same commit gives the same tarball twice is step 5 of [releasing.md](releasing.md). |

### Not run on the commit of v0.2.0

The full end-to-end test was last run on commit `e37ef4e` (2026-11-16).
On 2026-11-27 the test server had about 6 GB of free disk, and a run needs
about 22 GB, so it was not run again. The code that changed since:

- `51abb52`: the report lines of the start script are put in parentheses.
  Checked in a virtual machine: on three starts the reports still arrived
  and the screen stayed clean. No installation ran to the end with it.
- `126ac0a`: the wording when Setup is closed. Unit tests; seen in a
  virtual machine.
- `1fc1d87`: the interactive profile (B5).
- The fix for the drivers directory (B6). Unit tests and the upgrade test;
  an installation does not touch that code.

Running `make e2e` once on the tagged commit, before the draft is
published, would close this gap.

## Decisions

| Decision | Why |
| -------- | --- |
| The version is called v0.2.0, without "-alpha". | The maintainer's choice, 2026-11-27. The release workflow still marks the GitHub release as a pre-release, and nothing was tried on physical hardware. |
| Release notes live in `docs/releases/<tag>.md`, and the release workflow refuses to create a draft without them. | The notes of a release are then reviewed in the same way as the code, and a release cannot go out with the alpha's notes by mistake. |
| Armings made by v0.1.0-alpha last 24 hours from when they were made. | They have no end of their own. See ADR 0006. |

## Open questions for the maintainer

1. **Signatures of the release files.** The alpha's tag is signed; its files
   are not. `SHA256SUMS.asc` and a file with the public key would close
   that.
2. **The e-mail address in signed tags.** GitHub does not verify the alpha's
   tag because its address is not one of the account.
3. **Defects in the SMB library.** Unchanged from the alpha (ADR 0003).
